# Native task-boundary hook guardrails

Pleiad does not install a plugin-global hook. Bootstrap and upgrade manage .codex/hooks.json, scripts/pretool_handoff_guard.py, and scripts/validate_hooks.py only inside an adopted Pleiad repository. This prevents an enabled plugin from applying Pleiad policy to unrelated projects.

The project hook is synchronous PreToolUse policy for the observed Codex Desktop local-function names codex_app__create_thread and codex_app__send_message_to_thread; both current tool contracts carry the caller prompt in tool_input.prompt. Its command resolves the Git root with git rev-parse --show-toplevel and then runs the repository-local guard. It never uses PLUGIN_ROOT.

The guard extracts a Pleiad versioned envelope from tool_input.metadata (`handoff`, `envelope`, or `pleiad_handoff`) or from tool_input.prompt as complete JSON, fenced JSON, or `PLEIAD_HANDOFF: { ... }`. Captain CP/CO calls use `PLEIAD_CAPTAIN: { ... }` or metadata `captain_transport`, constructed by `captain_queue.transport_envelope` / the `transport` CLI with schema `captain-transport/v1`. Generated initial CO instructions include it. The compact envelope binds repository/issue, project/assignment and distinct recipient attempt UUIDs, generation, routing, standing authorization and operation. Create accepts `activate`; send accepts `continue` or `progress`. Missing or invalid envelopes are denied with `PLEIAD_HANDOFF_INVALID` before a supported native call. The old `agentic_sdlc_handoff` metadata key and `ASDLC_HANDOFF` prompt marker remain tested compatibility aliases for an installed v0.3.0 project; they are not canonical Pleiad forms.

## Enablement and coverage

After bootstrap or upgrade, open /hooks from the adopted repository, inspect the project hook definition, and trust its exact current hash. Codex skips changed non-managed command hooks until that review happens again. The managed configuration supplies POSIX and Windows commands, both resolving the guard from the Git root.

The guard covers only the two exact names above when they use Codex’s local-function hook path. Native spawn/follow-up/wait/results are intentionally not matched: native-cell assignment/result/checkpoint validation applies at meaningful boundaries through scripts/native_cell.py, without legacy cross-chat envelopes. The two top-level calls validate compact Captain boundaries for durable CP/CO transport and retain legacy validation for explicit legacy-top-level operation. The hook validates shape/routing/operation, not live queue admission, source identity or permission. Queue reservation/reconciliation, host-observed source bindings and native controls remain required; a copied valid envelope cannot establish them. The hook does not enforce subagent role identity or sandbox isolation. Codex documents that specialized tool paths can opt out of hooks; such a path is not an enforcement claim. If an actually required task-control path is unavailable or its boundary cannot be verified, retain the unresolved state, record sanitized observations and escalate through CO. Specialized paths outside this matcher must be reported as unverified hook coverage; do not claim a hook denial or hook enforcement there. Changing the matcher requires review, never an approval bypass. Hooks are local guardrails, not a durable transport authority; GitHub and committed artifacts remain authoritative.

## Host verification procedure

Run python scripts/validate_hooks.py from the adopted repository for the deterministic contract probe. Then, in a newly started Desktop session with the project hook trusted, invoke an invalid task creation/send envelope and verify the call is denied before side effects; invoke a valid envelope and verify the native call crosses the boundary. Record the exact tool names and result in the issue/PR. A running session cannot claim this final probe for a newly changed, untrusted hook.

## Candidate trust boundary

Candidate 0.1.6 changes the project hook definition's status message and the guard/runtime it invokes. Its hash differs from stable 0.1.5. The owner must review and trust the exact current hook definition through `/hooks` in a new session; this PR never trusts it automatically. A deterministic guard subprocess probe is not a live trusted-hook observation. CI and portable tests establish runtime behavior only. Live native observations, exact SHA, any unresolved coverage/approval limitation and independent results belong in the issue/PR evidence. Do not deliberately trigger destructive side effects to prove a denial.
